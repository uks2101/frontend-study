# Project Notes

상품 관리 서비스를 **직접 구현(1부) → 라이브러리 리팩터링(2부)** 순서로 만들며 겪은 문제와 설계 판단 기록.

## Problems

### 에러 없이 조용히 실패하는 오타

- Step 5 `cached.updateAt` (정답 `updatedAt`): 없는 속성이라 `undefined` → `Date.now() - undefined`는 `NaN` → `NaN < staleTime`은 항상 `false`. 캐시가 항상 "오래됨"으로 판단돼서, 뒤로 가기마다 불러온 페이지를 전부 다시 요청함. 화면은 캐시로 정상 표시돼서 Network 탭을 보기 전까지 몰랐음.
- Step 6 `detail_stock--low` (정답 `detail__stock--low`), Step 8 `taost` (정답 `toast`): 클래스명이 CSS와 안 맞아 스타일만 빠짐. 개발자도구 Elements에서 클래스를 보고 찾음.
- 공통점: JS는 없는 속성을 `undefined`로, CSS는 맞는 선택자가 없으면 그냥 무시 → **런타임 에러가 없음**.
- 교훈: 다음 프로젝트에서 TypeScript(없는 속성 접근을 컴파일 단계에서 잡음)와 CSS Modules(없는 클래스 참조를 잡음)를 써야 하는 이유.

### JSX에서 "문자열"과 "JS 값" 혼동

- `<label htmlFor="id">`: 따옴표 안이라 글자 그대로 `"id"`가 됨 → 파일 입력과 연결 안 돼서 [이미지 선택]이 동작하지 않음. `htmlFor={id}`가 맞음.
- `<h1>${title}</h1>`: `${}`는 템플릿 문자열(백틱) 안에서만 동작. JSX에서는 `$`가 글자로 출력됨.
- 정리: JSX에서 `"따옴표"`는 문자열 그대로, `{중괄호}`는 JS 값.

### Zustand selector 반환값을 구조 분해

- `const { items } = useCartStore((state) => state.items)`: selector는 **배열 자체**를 반환하므로 `{ items }`로 꺼내면 `undefined` → 장바구니 페이지 크래시.
- 1부의 `useCart()`는 `{ items }` **객체**를 반환해서 구조 분해가 맞았기 때문에 습관적으로 같은 모양으로 씀. lint와 build로는 잡히지 않음.

### StrictMode에서 요청이 2번 나가는 문제

- 개발 모드 StrictMode가 effect를 일부러 두 번 실행해서 같은 요청이 2번 나감.
- 막는 게 아니라 **두 번 실행돼도 문제없게** 만드는 게 정답: effect 정리 함수에서 `AbortController.abort()` → 첫 요청은 `(canceled)`.
- 같은 장치로 검색어를 빠르게 바꿀 때의 **레이스 컨디션**(늦게 온 옛 응답이 화면을 덮어씀)도 함께 해결됨.

### 삭제 후 페이지 보정 조건을 "근사"로 작성한 버그

- 처음엔 "현재 페이지 상품을 전부 지우면 이전 페이지로" 이동하게 만들었음.
- 마지막 페이지가 아닐 때(19페이지 10개 삭제, 20페이지에 상품이 남음)도 이동해버림. 뒤 페이지 상품이 당겨져 오면 19페이지는 그대로 있어야 함.
- 해결: 삭제 후 전체 페이지 수 `Math.ceil((total - 삭제 개수) / 페이지 크기)`를 **실제로 계산**해서, 현재 페이지가 범위를 넘을 때만 이동.

### 같은 컴포넌트를 두 곳에 렌더링할 때 id 중복

- 모바일 필터 Drawer에 사이드바와 같은 `PriceFilter`를 넣었더니, CSS로 숨긴 사이드바와 Drawer에 `id="min-price"`가 두 개 생김.
- `<label htmlFor>`가 문서에서 처음 나오는(숨겨진) 입력칸과 연결돼서 Drawer의 라벨이 동작하지 않음.
- 해결: 재사용 컴포넌트의 id는 `useId()`로 생성.

### TanStack Query로 교체 후 "다음 페이지 에러" 처리 차이

- 직접 만든 `useInfiniteQuery`는 첫 페이지 에러(`error`)와 다음 페이지 에러(`fetchNextPageError`)를 분리했음.
- TanStack Query는 다음 페이지가 실패해도 `status: 'error'`가 되고, `isFetchNextPageError`로 구분함.
- 그대로 두면 3페이지 실패 시 이미 본 40개가 사라지고 전체 에러 화면이 뜸 → `status === 'error' && !data`일 때만 전체 에러 화면을 보여주도록 수정.
- 교훈: 라이브러리로 바꿀 때 **이름이 같아도 동작이 다를 수 있다.**

## 설계 결정

### 필터 상태는 URL 하나에만 저장 (Single Source of Truth)

- 검색어·카테고리·가격·정렬을 `useState`가 아니라 URL 쿼리스트링에 저장 → 새로고침, 링크 공유, 뒤로 가기, 상세 갔다 오기에서 필터 유지.
- URL과 state 두 곳에 두면 동기화 버그가 생기므로 URL만 진짜 값으로 두고 화면은 URL을 읽어서 그림.
- 예외: 검색창은 "입력 중인 글자"(state)와 "확정된 검색어"(URL)를 나눔. 입력마다 URL을 바꾸면 요청이 매번 나가기 때문.
- 보기 방식(그리드/리스트)은 URL이 아니라 localStorage: "무엇을 보는가"는 공유 대상, "어떻게 보는가"는 개인 취향.
- 무한 스크롤의 `page`는 URL에 넣지 않고, 관리자 페이지네이션의 `page`는 넣음. "3페이지를 보고 있다"가 의미 있는지에 따라 다름.

### 계산할 수 있는 값은 state로 저장하지 않음

- `isLoading`/`isError`를 따로 두지 않고 `status` 하나로 → 불가능한 상태 조합 방지.
- `status`, 장바구니 총액, 폼 에러, `isDirty`, 갤러리의 현재 이미지 주소 모두 다른 값에서 계산.

### "어떤 조건에서 만든 상태인지"를 key와 함께 저장

- `useQuery`의 결과, 관리자 테이블의 선택 목록을 `{ key, data }` 형태로 저장하고 `key`가 현재 조건과 다르면 무시.
- 페이지를 바꿨는데 이전 페이지의 선택이 남아 보이지 않는 상품이 삭제되는 위험을 effect 없이 렌더링 시점에 막음.
- 같은 문제를 컴포넌트 단위로는 `key` prop으로 해결 (상품 상세, 수정 폼, 가격 필터).

### 직접 구현할 때부터 라이브러리와 같은 인터페이스로

- 직접 만든 `useQuery({ queryKey, queryFn: ({ signal }) => ... })`, `status: 'pending'`, `isPlaceholderData`, `useMutation`의 `onMutate/onError/onSettled`를 TanStack Query와 같은 이름·모양으로 설계.
- 2부에서 페이지 컴포넌트를 거의 수정하지 않고 import만 바꿔서 교체할 수 있었음.

### 장바구니 규칙은 순수 함수(reducer)에

- 재고 제한, 수량 합치기, 실행 취소 위치 복원 등 규칙을 `cartReducer`에 모음.
- Zustand로 옮길 때 reducer를 버리지 않고 `dispatch` 한 줄로 재사용 → 저장 위치(Context → Zustand)만 바뀌고 규칙은 그대로.

### 낙관적 업데이트와 조건부 롤백

- 삭제·재고 수정은 서버 응답 전에 캐시를 먼저 바꾸고, 실패하면 되돌림. 성공해도 마지막엔 무효화해서 서버 값으로 맞춤.
- 삭제는 스냅샷 전체 복원, 재고는 **"화면 값이 내가 바꾼 값일 때만"** 되돌림. 10→20(실패), 20→30을 연달아 하면 스냅샷 복원은 30까지 지우기 때문.
- 2부에서 `cancelQueries`로 "진행 중인 조회 응답이 낙관적 변경을 덮어쓰는" 경쟁 상황까지 해결 (1부에는 없던 부분).

### 되돌릴 수 있으면 "실행 취소", 없으면 "확인 창"

- 장바구니 삭제(브라우저 안의 데이터): 즉시 삭제 + 토스트 [실행 취소].
- 관리자 상품 삭제(서버 데이터, 모든 사용자에게 영향): `<dialog>` 확인 창.

### 스냅샷 저장의 트레이드오프

- 장바구니·찜·최근 본 상품은 담는 시점의 상품 정보를 저장 → 목록을 그릴 때 서버 요청이 필요 없음.
- 대신 관리자가 가격을 바꿔도 장바구니에는 옛 가격이 남음. 실서비스라면 결제 직전에 서버에서 가격·재고를 다시 확인.
- 이미지는 data URL로 저장했지만, 실서비스는 파일 저장소(S3 등)에 올리고 URL만 저장.

## 1부 vs 2부 비교

### 전역 상태: Context → Zustand

| | Context / 직접 구현 | Zustand |
|---|---|---|
| 인프라 코드 | 164줄 (6개 파일) | 71줄 (4개 파일) |
| Provider | 2개 (순서 주의) | 0개 |
| 다시 그려지는 범위 | Context를 읽는 컴포넌트 전부 | selector 결과가 바뀐 컴포넌트만 |
| 상태/액션 분리 | Context 2개로 직접 분리 | 액션은 바뀌지 않으므로 자동 |
| 컴포넌트 밖에서 사용 | 불가 | `getState()`/`setState()` (예: `toast.success()`를 어디서든 호출) |

- 중간 단계로 `useSyncExternalStore` 기반 스토어를 직접 만들어 본 뒤 Zustand로 교체 → Zustand의 원리(외부 스토어 + selector 구독)를 이해하고 씀.
- selector에서 매번 새 배열을 만들면 무한 렌더링이 되는 이유도 이 원리에서 나옴.

### 서버 상태: 직접 구현 → TanStack Query

| | 직접 구현 | TanStack Query |
|---|---|---|
| 코드 | 250줄 (4개 파일) | 설정 10줄 |
| 요청 취소, 캐시, staleTime, 이전 데이터 유지, 무한 스크롤, 무효화, 낙관적 업데이트 | ✅ | ✅ |
| 자동 재시도 | ❌ | ✅ (404 제외 1회로 설정) |
| 중복 요청 합치기 | ❌ | ✅ |
| 창 포커스 시 갱신 | ❌ | ✅ |
| 안 쓰는 캐시 정리 (gcTime) | ❌ 계속 쌓임 | ✅ |
| 진행 중 요청 취소 (cancelQueries) | ❌ | ✅ |
| DevTools | ❌ | ✅ |

- 직접 만들어 보니 라이브러리가 "편의 기능"이 아니라 **놓치기 쉬운 경쟁 상황과 메모리 관리**를 해결해 준다는 걸 알게 됨.
